gz-rendering & gz-gui & O3DE: how a pixel reaches your screen

Three big pieces of software cooperate to draw a Gazebo scene when the experimental O3DE backend is active. This page traces how a single rendered pixel travels from O3DE / Atom all the way to your monitor, who calls what, and where the current bug lives. Written for an expert developer who is not a graphics expert.

A few words first

The same word means different things in different contexts. Just enough definitions so the diagrams make sense:

GPU memory
Like RAM but on the graphics card. Vulkan calls a block of GPU memory a VkDeviceMemory. The CPU usually cannot read it directly.
VkImage
A 2D (or 3D) array of pixels that lives in GPU memory. Think "GPU-side picture". Anything that gets rendered to lives in a VkImage.
VkDevice
A connection to the GPU. Each independent component using Vulkan typically has its own VkDevice. O3DE has one; Qt has another; both talk to the same physical GPU but they do not share Vulkan objects by default.
File descriptor (FD), Vulkan flavor
A small integer the Linux kernel uses to identify shared resources. Vulkan's VK_KHR_external_memory_fd extension lets one VkDevice say "here's an FD pointing at this GPU memory" and another VkDevice (even in another process) can use that FD to map the same memory. This is how we do zero-copy interop. More on this below.
Swapchain
The short ring of VkImages the window-system-integration (WSI) uses to present to the screen. Usually 2 or 3 images cycling. More on this below.
Render pass / FBO
A Vulkan render pass is a unit of drawing that targets a set of "attachments" (color images, depth, ...). An offscreen render target a.k.a. FBO (Framebuffer Object) is a render pass whose color attachment is a regular VkImage you keep around (not directly shown to the user).
QSG (Qt Scene Graph)
Qt's high-performance UI renderer. It builds a tree of nodes (rectangles, text, images, …) and rasterizes them efficiently. More on this below.
QRhi
Qt's internal Rendering Hardware Interface: an abstraction over Vulkan / OpenGL / Metal / Direct3D. Each QSG node ultimately produces QRhi calls; QRhi turns them into native API calls.

The three layers

Three independent codebases. Each one owns part of the work; the interesting question is the seams between them.

The three actors, left to right. Atom does the drawing, gz-rendering shepherds the image across, gz-gui shows it.

Importantly: Atom and Qt each open a separate connection to the GPU (their own VkDevice). That's why the seam between them needs the file-descriptor handshake described in section 5.

A point worth pausing on: at step 3, the import does not copy any pixels. Both Atom's VkImage "A" and Qt's VkImage "B" share the same physical bytes of GPU memory. When Atom finishes rendering, Qt can immediately read what Atom drew. That's the "zero-copy" in "zero-copy interop".

The seam between steps 3 and 4 is also unusual: Qt did not allocate that VkImage. Qt is being told "here is a foreign-owned image; please treat it as a texture". The Qt API for this is QSGVulkanTexture::fromNative(VkImage, layout, window, size).

What is a "swapchain"?

The screen refresh and the GPU don't naturally agree on timing. The swapchain is Vulkan's solution: it owns a small ring of VkImages, typically 2 or 3. At any moment, one is being shown to the user, one is being rendered into, and the others are queued. Calling vkQueuePresentKHR(image_index) says "the image I just rendered into is image_index; please show it next".

Swapchain images cycle through ‘rendering’ → ‘queued’ → ‘on screen’. Qt fills the next one; the WSI shows it.

The reason the swapchain matters for this story: Qt does not render directly into the swapchain in the natural-looking way you might imagine. After Qt's window resizes (e.g. when the gz-gui window goes to full size), Qt's pipeline becomes:

  1. Render the scene graph (your textured nodes, QML rectangles, …) into a private offscreen image — call it the "FBO".
  2. To present, start a render pass on the next free swapchain image, clear it to black, then draw one fullscreen triangle that samples the FBO across the whole screen.
  3. Hand the swapchain image to vkQueuePresentKHR.

Step 2's "one fullscreen triangle that samples a texture" is a standard GPU trick: a triangle that's larger than the screen but gets clipped to the viewport, so every pixel of the swapchain runs the same texture-sample shader. The point is: whatever ends up in the FBO is exactly what the swapchain (and your screen) will show.

What's "FD" in Vulkan land?

In Linux generally, a file descriptor (FD) is a small integer the kernel uses to identify an opened resource (a file, a socket, …). It's cheap to pass around — just an int — but it refers to something big the kernel knows about.

Vulkan's VK_KHR_external_memory_fd extension lets you do the same trick for GPU memory: 

// O3DE side (in gz-rendering):
int fd;
vkGetMemoryFdKHR(&getFdInfo, &fd);   // fd = some integer like 219

// hand ‘fd’ to gz-gui via a normal C++ API call.

// Qt side (in gz-gui):
VkImportMemoryFdInfoKHR import{};
import.handleType = VK_EXTERNAL_MEMORY_HANDLE_TYPE_OPAQUE_FD_BIT;
import.fd         = fd;
VkMemoryAllocateInfo alloc{ .pNext = &import, ... };
vkAllocateMemory(qtDevice, &alloc, nullptr, &qtMemory);
// vkBindImageMemory(...) attaches a fresh VkImage to that memory.
// Now Atom and Qt share the same physical GPU bytes.

This is the "zero-copy" path. Without the FD trick, you would have to copy pixels from Atom's VkImage to CPU RAM, then upload them to Qt's VkImage — doable, but slow. With the FD trick, the bytes never move.

The FD itself is just a tiny integer crossing the software seam. The GPU memory it refers to is large and stays put.

Caveat that bit us: on NVIDIA's proprietary driver, an OPAQUE_FD image used cross-device must be a dedicated allocation (chained with VkMemoryDedicatedAllocateInfo) and bound at offset 0. That's how the gz-rendering code does it; without it, the importing device samples wrong addresses (the driver bakes assumptions into its texture units that only hold when the image owns its allocation). See the findings doc for the gory detail.

What is QSG?

Qt has two parallel rendering stacks: one for traditional widgets (QPainter), and one for declarative .qml scenes — the Qt Scene Graph, abbreviated QSG. QSG is heavily optimized: instead of "draw this rectangle, then draw this text, then draw this image" one call at a time, the QML engine builds a tree of QSGNode instances that describe the whole scene, and the QSG renderer batches it into GPU draw calls.

QML → QSG node tree → Vulkan draw calls. Our box-from-Atom is the pink QSGSimpleTextureNode in the middle.

QSGSimpleTextureNode is the simplest QSG node that draws a textured quad. Our gz-gui MinimalScene puts one of these in the QSG tree every frame; the texture it uses is the fromNative wrap of the Atom-rendered VkImage. That's our hand-off to Qt's scene graph.

Who calls which API

Pulling the previous sections together: when a frame happens, here is who calls what.

LayerWhat it doesAPIs it actually calls
O3DE / Atom Renders the scene (box, sphere, cylinder) into a VkImage on its own VkDevice. Knows nothing about Qt. Vulkan core: vkCmd*, vkQueueSubmit, vkCreateImage with VkExternalMemoryImageCreateInfo, vkAllocateMemory with VkExportMemoryAllocateInfo.
gz-rendering The O3DE plugin (o3de/src/O3deBackend.cc, O3deCamera.cc) sets the Atom side up to export, then reaches across to gz-gui with the FD + size + VkImage handle. Atom's C++ API (creating scenes, lights, cameras, drawing primitives) plus vkGetMemoryFdKHR for the export.
gz-rendering The CPU-readback fallback path (O3deRenderTarget::Copy) for engines that don't want zero-copy. Atom's AttachmentReadback + a buffer copy to a gz::common::Image.
gz-gui The Vulkan path in plugins/minimal_scene/ MinimalSceneRhiVulkan.cc: import the FD, wrap the resulting VkImage as a QSGTexture, install it in the QSG tree. A small bit of Vulkan: vkAllocateMemory with VkImportMemoryFdInfoKHR, layout transitions / QFOT-acquire. Then Qt: QNativeInterface::QSGVulkanTexture:: fromNative, QSGSimpleTextureNode, the QQuickItem scene-graph protocol.
gz-gui (Qt) Qt's QSG/QRhi internals: rasterize the tree, present. Vulkan again, but called by Qt itself: vkCmdBeginRenderPass, vkCmdBindPipeline, vkCmdBindDescriptorSets, vkCmdDraw, vkQueuePresentKHR.

So Vulkan is called from all three layers, but each layer calls a small, specific subset:

O3DE / Atom

Heavy Vulkan: full render pipeline. Owns one VkInstance + VkDevice.

gz-rendering's o3de plugin

Light Vulkan: just enough to export GPU memory as an FD. Mostly calls Atom's C++ API.

gz-gui's MinimalScene

Light Vulkan: import the FD, set image layouts. Most of its work is Qt scene-graph plumbing. Qt itself issues the heavy Vulkan to draw + present.

Where the current bug is

The "uniform grey 148 on screen" symptom is in section 5 of the journey — but specifically in the step where Qt's scene graph renders into the offscreen FBO before composing it onto the swapchain.

The same journey from above, annotated with what we proved. The red pulsing box is the failure point.
So what is the failure, in one sentence?
Qt's QSGSimpleTextureNode, holding a fromNative wrap of a foreign-owned VkImage that is known-correct on Qt's own VkDevice, does not deliver the texture's pixels into the offscreen FBO when QSG rasterizes the scene. The FBO ends up filled with the QML background colour (148, Atom's clear), and Qt's faithful fullscreen-triangle composite then writes 148 across the whole swapchain.

How we verified each piece

  • Atom's image is correct: two independent in-tree tools (GZ_O3DE_DUMP_PNG and GZ_O3DE_SAMPLE_PROBE) read the imported VkImage on Qt's device and produce byte-identical PPMs containing the shapes.
  • fromNative wraps the right handle: we added gated diagnostic prints (GZ_GUI_VULKAN_DIAG=1) in MinimalSceneRhiVulkan that log the VkImage handle every frame; it matches the producer's.
  • The swapchain present path is empty…ish: the VK_LAYER_GZ_swapchain_dump Vulkan layer (gz-gui test/regression/swapchain_dump_layer/) hooks vkQueuePresentKHR and dumps the about-to-be-presented image to PPM. With its GZ_SWAPCHAIN_DRAW_TRACE=1 mode enabled, the layer traces every render-pass and draw. Post-resize, the swapchain pass is "clear to black + one fullscreen triangle samples one texture + end" — faithful to whatever that texture contains. So the 148 must be in the texture (= the FBO).
